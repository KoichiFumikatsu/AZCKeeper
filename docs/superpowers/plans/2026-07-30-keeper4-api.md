# Keeper 4 — API backend · Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** Construir el backend PHP de Keeper 4 sobre el esquema nuevo (36 tablas), empezando por el corte
vertical que entrega la prioridad #1 (vista de procesos) end-to-end: handshake con recorte por tier,
ingesta de episodios, y lectura de la vista de procesos.

**Architecture:** Backend nuevo bajo `AZCKeeper_Client/WebK4/`, en paralelo al `Web/` de Keeper 3 (que
queda intacto hasta retirarse). Reutiliza la infra probada (`Http`, `Config`, `RateLimiter`,
`InputValidator`, `AuthService`, patrón de repos con `PDO` por parámetro). Docroot de DEV
`devkeep.azclegal.com` apunta a `WebK4/public`.

**Tech stack:** PHP 8, MySQL 8.0.40, sin composer (require_once en bootstrap). El header `Authorization` NO
se propaga en este hosting → auth por `X-Auth-Token` (fallback ya en `Http::bearerToken`).

**Specs de diseño:** `2026-07-29-keeper4-datos-y-vista-procesos.md`, `2026-07-30-keeper4-tiers-y-features.md`,
`2026-07-30-keeper4-inventario-cobertura.md`.

## Global Constraints

- Entorno: `devkeep.azclegal.com` + `pipezafra_keepdev`. **Producción NO se toca.**
- Charset `utf8mb4_general_ci`. Repos reciben `PDO` por parámetro (nunca `Db::pdo()` interno).
- Cero SQL de negocio en endpoints; todo en repos. Auth con `AuthService::requireSession()`.
- Comandos SSH simples, uno por conexión (límite de forks del hosting).
- Rama `feature/modulo-seguridad`. Un commit por tarea.

## Alcance de este plan (corte vertical) vs. lo que queda

**En este plan (vertical verificable en DEV):**
- T1: Fundación — `WebK4/` con Config, Db (esquema nuevo, sin legacy fallback), Http, bootstrap, router.
- T2: `TierResolver` — módulos efectivos de una firma (tier − revocados + concedidos, o todos si enforcement off).
- T3: Handshake — resuelve política (global→user→device), la recorta contra el tier, devuelve effectiveConfig.
- T4: Ingesta de episodios — `POST /client/episodes/batch` → `keeper_episode`, actualiza `keeper_episode_daily`.
- T5: Vista de procesos — `GET /admin/process-view` (resumen del período + detalle paginado, orden cronológico).

**Fuera de este plan (fases siguientes, documentadas):** día-resumen sin GREATEST, cola de comandos,
ingesta de screenshots/location, recálculo de doble empleo, `keeper_device_module_state` echo, enrolamiento,
Metrics service, y todo el panel + cliente C#.

## Task 3: Handshake con recorte por tier

**Files:**
- Create: `AZCKeeper_Client/WebK4/src/Repos/PolicyRepo.php` (lee global/user/device)
- Create: `AZCKeeper_Client/WebK4/src/PolicyService.php` (deepMerge con listas que se reemplazan — el fix de la Fase 0)
- Create: `AZCKeeper_Client/WebK4/src/Endpoints/ClientHandshake.php`

**Interfaces:**
- Consumes: `TierResolver`, `SessionRepo`, `DeviceRepo`.
- Produces: `POST /client/handshake` → `{ok, policyApplied:{composition}, effectiveConfig, ...}`.
  `effectiveConfig.modules` ya recortado: un módulo que el tier no permite queda en `false`.

- [ ] **Step 1: PolicyRepo + PolicyService**

`PolicyRepo::getAllPolicies` (global cache + user/device en un UNION, como K3). `PolicyService::deepMerge`
con el fix de listas (`array_values($v) === $v` → reemplaza, no combina por índice).

- [ ] **Step 2: Handshake resuelve y recorta**

Compone global→user→device, luego resuelve la firma del usuario
(`keeper_user_assignments.firma_id`), obtiene módulos efectivos vía `TierResolver`, y **fuerza a `false`
en `effectiveConfig.modules` todo módulo que el tier no permita**. Devuelve `composition` (las capas).

- [ ] **Step 3: Verificar en DEV** — sembrar usuario+device+sesión+firma con tier, golpear handshake con
  `X-Auth-Token`, confirmar que un módulo fuera del tier llega en `false` aunque la política lo pida.

- [ ] **Step 4: Commit**
